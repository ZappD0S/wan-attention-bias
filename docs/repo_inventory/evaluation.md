# Evaluation inventory

## Scope and current contents

`evaluation/` is a GPU-heavy video/action-consistency evaluation package. Tracked Python entry points are `main.py`, `engine.py`, `auditor.py`, `sam2_pipeline.py`, `utils.py`, and the package initializers. The repository currently also has untracked files `evaluation/run.sh`, `evaluation/old_prompts.txt`, `evaluation/videobench/engine.py`, and `evaluation/videobench/original.py` (as reported by `git status`). Ignored, present artifacts include `input_video.mp4`, `logs/`, `output/`, and Python `__pycache__` directories. There is no `evaluation/configs/` or separate `evaluation/prompts/` directory: prompt material is embedded in `auditor.py` and `videobench/prompts.py`; `old_prompts.txt` is an unused legacy prompt set.

`evaluation/output/` is currently empty. `evaluation/input_video.mp4` is a standalone ignored sample and is not referenced by the current entry point. `evaluation/logs/` is a large ignored working tree: 402 per-video directories contain 804 `obj_0.mp4`/`obj_1.mp4` crop artifacts (about 469 MB total), plus 22 top-level log files. `debug_eval.log` contains model reasoning/debug output (about 10.9 MB); `evaluation.log`, `evaluation.log.old`, and timestamped `log_*.log` files contain model-loading/progress/table output, including prior runs. These artifacts are outputs/history rather than a checked-in dataset or result schema; no JSON result writer is present.

## Architecture and execution flow

1. **Entry point and task discovery (`main.py`).** Run as `python -m evaluation.main`. `EvaluationPipeline` scans immediate child directories of `--videos-dir`, excluding `debug` and dot-prefixed names (`main.py:48-74`). Each accepted directory must have `config.json` and files matching `video_\\d+\.mp4`. The config is expected to contain `params`, `prompt_data.bboxes`, and `prompt_data.action_prompts.split_sentences.segments`; the segment first elements become action descriptions (`main.py:64-90`). The implementation currently assumes exactly two bboxes, two segments, and two returned crops (`main.py:105-113`), despite calculating the progress total from the config values.
2. **Segmentation/cropping (`sam2_pipeline.py`).** For every source video, OpenCV reads all frames as RGB and computes an integer stride from source FPS and the requested 16 FPS (`sam2_pipeline.py:12-26`). `SAM2VideoPredictor.from_pretrained("facebook/sam2-hiera-large")` is initialized, each config bbox is seeded at frame zero, and masks are propagated (`sam2_pipeline.py:115-132`). For each object, the union of per-frame padded boxes defines one fixed output canvas; other object masks are blacked out and pixels outside the object's per-frame visibility box are zeroed before writing `obj_N.mp4` at the configured output location (`sam2_pipeline.py:134-189`). `get_crop_and_mask`, `apply_mask_overlay`, `finalize_frame`, and `create_video_writer` are retained helpers but are not used by `run_sam2_pipeline`.
3. **Model engine (`engine.py`).** `QwenEngine` loads Qwen3-VL-8B-Instruct by default (or Qwen2.5-VL when requested), in bfloat16 with `device_map="cuda:0"`, and loads its `AutoProcessor` (`engine.py:17-28`). It packages optional video plus text through `qwen_vl_utils.process_vision_info`, supplies even `nframes` based on OpenCV frame count, and performs deterministic generation up to 2048 tokens (`engine.py:30-99`). `get_scoring_logits` replays prompt/reasoning/score-turn messages and returns last-position logits (`engine.py:101-152`). `calculate_soft_score` converts target strings to token IDs, normalizes their probability mass, and returns a weighted expected score (`engine.py:154-194`).
4. **Auditors (`auditor.py`).** `VideoAsset` lazily asks Qwen for a chronological, observable-only description, caching it for that object (`auditor.py:12-35`). `ActionAuditor.score_pair` subtracts the score for action B from action A (`auditor.py:38-49`). Soft direct and blind auditors use a generated reasoning turn followed by logits over 1–5; blind variants score only the cached text description (`auditor.py:71-102`, `148-183`). `SoftTwoAFCAuditor` uses logits over A/B and returns a pairwise margin (`auditor.py:105-145`). Discrete auditors request a textual `Score: X` and parse/clamp the final digit (`auditor.py:51-68`, `186-238`).
5. **Aggregation and reporting (`main.py`).** Each object crop is paired with its corresponding action and the other action as the negative; margins and positive-margin counts are collected (`main.py:107-133`). `utils.py` makes nested parameter dictionaries hashable, groups repeated parameter settings, and rejects a narrow subset-key ambiguity (`utils.py:15-59`). Statistics are a one-sided binomial test and 10,000 bootstrap resamples of margins (`main.py:151-169`). Results are printed as a Rich table for five active auditors—soft 2AFC, soft direct/blind, and discrete direct/blind (`main.py:243-279`). The commented `videobench` entry is not executed.

The current flow therefore performs SAM2 once per source video **for every auditor**, writes/overwrites the same `obj_N.mp4` names, then makes multiple Qwen calls per crop. `--output-dir` receives crop videos and `debug_eval.log`; the final statistics are displayed but not persisted by `main.py`.

## VideoBench subtree

`videobench/` is a partially ported VideoBench-style multi-turn evaluator. `prompts.py` defines the system prompts for blind observation, two question agents, reflection, and 1–3 scoring (`prompts.py:1-217`). `agents.py` adapts that protocol to the local `QwenEngine`: `VideoHost.blind_observation` sends video to Qwen, two `TextAgent`s ask text-only follow-up questions, `reflection` sends video plus the questions, and `final_score` sends both descriptions plus video (`agents.py:9-149`). `RobustParser` extracts bracketed sections/questions and heuristically parses a 1–3 score (`robust_parser.py:4-105`). `VideoBenchAuditor._score` composes those four stages and returns a float (`evaluate.py:7-24`); inherited `score_pair` can then compare two action prompts. `videobench/__init__.py` exports only this adapter.

`videobench/original.py` is an unintegrated OpenAI implementation retained as reference. It defines API-backed `Agent`/`Host` conversation classes, image-frame message construction, legacy result extraction, and an `eval` loop. It expects a missing sibling `.utils.Video_Dataset`, OpenAI API configuration keys, and a JSON frame dataset. `videobench/engine.py` is another unused Qwen engine variant with a different `generate(system_prompt, user_text, video_path)` signature. Neither file is called by the current main flow; the active adapter uses `evaluation.engine.QwenEngine`, while the original and alternate engine should be treated as stale/reference code.

## Scripts, inputs, outputs, and environment

- `evaluation/run.sh:3-13` creates `evaluation/logs` and `evaluation/output`, mounts a hard-coded remote SSHFS path at `evaluation/output` if it is not already a mountpoint, and invokes the repository-root `run.sh`. Thus it requires SSHFS, remote access, the expected remote path, and a working mountpoint command.
- `evaluation/job.oar:1-50` is an OAR/Grid’5000 batch wrapper. It loads Apptainer, requires `nvidia-smi`, accepts `PARAM_CONFIG_NAME` as its first argument or environment variable, maps `/storage/attn_bias/output_videos/<name>` as both input and output, and runs for a declared 48-hour walltime.
- The root `run.sh` selects Apptainer/Singularity, sources `.env`, requires a CUDA image (`CONTAINER_IMAGE` or `containers/cuda_ubuntu.sif`), binds the project and Hugging Face cache, passes `HF_TOKEN`, and adds `--nv`. Relative paths therefore depend on launching from the repository root; GPU, container runtime/image, CUDA drivers, model-cache or Hugging Face access, and writable temporary/cache storage are assumed.
- Relevant declared dependencies in `pyproject.toml` include PyTorch/CUDA, Transformers, Qwen VL utilities, OpenCV, SAM2, torchvision/torchcodec, NumPy/SciPy, Rich, tqdm, and Hugging Face tooling. `Qwen/Qwen3-VL-8B-Instruct` and `facebook/sam2-hiera-large` are downloaded or loaded externally; the code hard-codes CUDA and bfloat16 rather than offering CPU/device CLI options.
- Expected input is a generated-video directory tree with one `config.json` and `video_N.mp4` files per child directory. Expected intermediate output is one pair of masked object videos per child directory. The only durable textual output implemented is the debug log; scores are console output. Existing log artifacts show prior progress/table output and are not consumed by the code.

## Cursory issues and documentation/test gaps (repository as-is)

- **Input validation is thin.** Missing `videos_dir`, `config.json`, required keys, empty videos, malformed bboxes, or zero FPS fail through uncaught exceptions; `frames[0]` is used without an empty-video check (`main.py:50-72`, `sam2_pipeline.py:111-113`). There are no evaluation tests or documented example config schema.
- **Hard-coded cardinality and assumptions.** The pipeline asserts exactly two crops/actions (`main.py:105-106`) and indexes the opposite action (`main.py:110-111`), while its discovery code otherwise counts arbitrary numbers of bboxes/segments (`main.py:66-72`). Directory and file iteration is unsorted (`main.py:50-62`), so ordering is not explicitly stable.
- **Progress/accounting and repeat work are easy to misread.** The progress total counts each crop/action call, but each pair is scored by two auditor calls and progress advances by two (`main.py:79-81`, `107-122`); this is correct only for the enforced two-by-two setup. SAM2 is rerun for each of five auditors and overwrites the same crop paths rather than caching them, creating substantial avoidable work (`main.py:263-265`, `sam2_pipeline.py:153-154`).
- **Frame-rate and geometry assumptions.** Frames are subsampled by integer FPS stride but output metadata is always `target_fps`, which can be inaccurate when source FPS is not an exact multiple (`sam2_pipeline.py:15-16`, `155-159`). Bounding-box maxima are used without the usual `+1` extent (`sam2_pipeline.py:90-99`), and the global dimensions are rounded down to even values; no writer-open/codec check is made.
- **Potential portability/runtime hazards.** `sam2_pipeline.py` imports `suppress_tqdm` as `from utils import ...` rather than a package-relative import (`sam2_pipeline.py:9`), so importing it outside the repository-root module path can resolve incorrectly. `set_seed` unconditionally calls CUDA seed functions (`main.py:172-179`), and the engine unconditionally loads to `cuda:0` (`engine.py:24-26`).
- **Soft scoring has model/tokenization caveats.** Only the first token of each encoded target is used and target/weight lengths are not checked (`engine.py:159-175`, `192-194`); tokenization of standalone versus context-prefixed `A/B` or digits can affect the score. If there are no margins, bootstrap means and the binomial calculation are not guarded (`main.py:152-163`).
- **VideoBench wiring is stale/incomplete.** The production registration is explicitly commented out (`main.py:249`); `original.py` references missing `.utils.Video_Dataset` (`original.py:11`) and uses `modelname` before it is assigned in `eval` (`original.py:381-403`). Its `Host.answer` can leave `description` unbound when the expected response markers are absent (`original.py:254-260`). The alternate engine has an incompatible interface with the adapter and is unused (`videobench/engine.py:12-20`, `agents.py:79-84`).
- **Parsing is permissive in some places and brittle in others.** Discrete parsing requires a literal `Score:` line (`auditor.py:57-68`), while VideoBench fallback parsing may take arbitrary digits from the last line and clamps unrelated values to 1–3 (`robust_parser.py:90-102`). Prompt tags differ between examples and extraction conventions (`prompts.py:19-29`, `agents.py:112-115`), with no parser unit tests.
- **No test/documentation harness is present.** The only validation performed here was cheap Python AST syntax parsing of all `evaluation/**/*.py` files; it does not import heavy dependencies or execute inference. There are no evaluation-specific tests, schema fixtures, reproducibility notes, result serialization format, or operational documentation for the remote mount/config layout. Existing ignored logs and crop videos provide run evidence but not a verifiable expected-result fixture.
